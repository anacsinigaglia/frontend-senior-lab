Módulo · Carregamento e rede

Envie menos, mais tarde e na ordem certa

A tela fica pronta mais cedo quando o navegador baixa só o que precisa agora, descobre cedo o que é crítico e adia o resto. E o servidor aguenta mais quando o cliente não dispara cem requisições de uma vez. Aqui você divide um bundle, adia imagens, reordena a cascata de downloads, pré-carrega a próxima tela e limita a concorrência.

  • Sabe o que vai no primeiro downloadAbre o analisador de bundle antes de discutir framework.
  • Adia o que não é visívelTelas, bibliotecas e imagens fora da tela carregam quando forem usadas.
  • Protege o servidorLimita requisições simultâneas e pede endpoint em lote em vez de cem chamadas.

Experimento · Tree shaking, code splitting e dynamic import

O que vai no primeiro download?

Um app de gestão com três telas. A pessoa abre a tela Início. Ligue as técnicas uma a uma e veja quanto JavaScript sai do download inicial e passa a carregar só quando for usado.

TécnicaO que fazQuem faz
Tree shakingRemove do bundle o código que foi importado mas nunca usadoO bundler (Vite, webpack, Turbopack), desde que o código use import/export (ES modules) e não tenha efeitos colaterais ao ser importado
Code splittingDivide o bundle em pedaços (chunks) que carregam separadosO bundler, a cada import() dinâmico. Frameworks como Next e React Router dividem por rota sozinhos
Dynamic importimport('./x') devolve uma Promise e cria um chunk novoVocê, no ponto em que o código passa a ser necessário (clique, rota, modal)
Lazy loadingAdia o carregamento até o recurso ser necessário ou ficar visívelReact.lazy e next/dynamic para componentes; loading="lazy" para imagens e iframes
Rede

Tamanhos em KB comprimidos (gzip), na ordem de grandeza de bibliotecas reais. O tempo de execução é uma estimativa grosseira para um celular médio: cerca de 2,5 ms por KB comprimido para o navegador analisar, compilar e rodar.

Barra cheia: vai no download inicial. Barra listrada: chunk separado, baixado só quando for usado.

Um import() de verdade

O botão abaixo roda import('./chunks/relatorio.js'). Abra a aba Network do DevTools antes de clicar: o arquivo só aparece na lista depois do clique, e o segundo clique não baixa de novo.

Como encontrar o que pesa

Otimizar bundle sem olhar o bundle é chute. As ferramentas abaixo mostram cada dependência como um retângulo do tamanho que ela ocupa.

Analisar

Analisador de bundle

  • Vite: rollup-plugin-visualizer.
  • Next: next experimental-analyze (Turbopack) ou @next/bundle-analyzer.
  • Antes de instalar um pacote: bundlephobia.com mostra o tamanho e se aceita tree shaking.
Suspeitos comuns

O que costuma pesar

  • Bibliotecas de data com todos os idiomas, gráficos, editores, mapas, PDF.
  • Pacotes duplicados em versões diferentes.
  • Barrel files (index.ts que reexporta tudo) com efeitos colaterais.
  • Polyfills para navegadores que você não suporta.
O custo de dividir

Chunk demais também atrapalha

  • Cada import() é uma ida à rede no momento do uso: a pessoa vê um loading que antes não existia.
  • Dividir algo de 3 KB não compensa.
  • Pré-carregue o chunk quando o uso é provável (ao passar o mouse, no tempo ocioso).
O que conta

Orçamento de performance

Defina um teto para o JS inicial (por exemplo, 170 KB comprimidos para celular) e faça o CI falhar quando passar, com size-limit ou o relatório do bundler. Sem isso, o bundle só cresce.

Leitura de sênior. O JavaScript custa duas vezes: para baixar e, principalmente, para o celular analisar e rodar, enquanto a thread principal fica ocupada (o que piora o INP). Imagem do mesmo tamanho é muito mais barata. Divida por rota (o framework costuma fazer isso), adie o que só aparece depois de um clique e meça antes e depois com o analisador.

Experimento · Lazy loading de imagens

Quarenta fotos, quantas a pessoa vê?

Uma vitrine com 40 fotos de 120 KB, das quais só umas quatro cabem na tela. Sem lazy loading, todas são pedidas ao abrir a página e disputam a banda com o que está visível. Com lazy loading, cada foto é pedida quando chega perto da tela. Role a vitrine nos dois modos.

Carregamento

O modo lazy usa IntersectionObserver com uma margem de 150 px, o mesmo princípio do loading="lazy" nativo: a foto é pedida um pouco antes de aparecer, para já estar pronta quando chegar.

0fotos pedidas
0baixados
0pedidas e nunca vistas
Ver o código

Abaixo da dobra: lazy

<img src="produto-12.avif" alt="…"
     width="400" height="300"     // reserva o espaço (CLS)
     loading="lazy" decoding="async">

// Next.js: next/image já é lazy por padrão
<Image src={foto} alt="…" width={400} height={300} />

A imagem principal (LCP): nunca lazy

<img src="capa.avif" alt="…" width="1200" height="600"
     fetchpriority="high">        // pede primeiro

// Next.js 16: preload substitui o antigo priority
<Image src={capa} alt="…" preload />
// ou loading="eager" / fetchPriority="high"

Leitura de sênior. Lazy loading é para o que está fora da tela. Colocar loading="lazy" na imagem principal é um erro comum que atrasa o LCP, porque o navegador espera o layout para decidir se ela está visível. Junto com o lazy, sirva o tamanho certo (srcset/sizes), em AVIF ou WebP, e sempre com width e height.

Experimento · Preload, preconnect e fetchpriority

Quem o navegador descobre tarde?

O navegador só baixa o que já descobriu. A fonte só aparece depois que o CSS é lido; os dados do app, depois que o JavaScript roda. Cada descoberta tardia vira um degrau na cascata. Ligue as dicas de recurso (resource hints) e veja os degraus sumirem.

Conectar a um domínio novo (DNS, TCP e TLS) custa 250 ms neste modelo. Sem prioridade alta, a imagem principal divide a banda com o JavaScript.

Leitura de sênior. Dicas de recurso não deixam nada mais leve: elas só antecipam. Por isso funcionam para o que é crítico e descoberto tarde, e atrapalham quando usadas em tudo. Abra a aba Network, ordene pela coluna Waterfall e procure o degrau: um recurso importante que começa só depois de outro terminar.

Experimento · Prefetching

Começar a buscar antes do clique

Cada tela leva 700 ms para chegar do servidor. Sem prefetch, a pessoa espera tudo isso depois de clicar. Com prefetch, a busca começa antes: quando o mouse passa por cima ou quando o link aparece na tela. Experimente cada modo e compare a espera depois do clique com o que foi buscado à toa.

Next.js: o <Link> faz sozinho (em produção)

// prefetch quando o link aparece na tela; em rota dinâmica,
// só até o loading.tsx mais próximo

<Link href="/relatorios" prefetch={false}>   // telas pesadas e raras

React Query: dados ao passar o mouse

<a href="/clientes/42"
   onMouseEnter={() => queryClient.prefetchQuery({
     queryKey: ['cliente', 42],
     queryFn: () => api.cliente(42),
   })}>

// Chunk de uma tela lazy: chame o import() antes
onMouseEnter={() => import('./telas/relatorios')}

Leitura de sênior. Prefetch troca dados e servidor por velocidade percebida. "Ao passar o mouse" acerta quase sempre e desperdiça pouco: a pessoa leva de 100 a 300 ms entre passar o mouse e clicar. "Quando aparece" é o mais rápido e o que mais desperdiça. Desligue o prefetch em links para telas pesadas e raras, e respeite navigator.connection.saveData.

Experimento · Concorrência limitada

Cem requisições de uma vez derrubam quem?

Atualizar a cotação de 40 contratos chamando a API uma vez para cada. A API simulada aguenta 6 requisições ao mesmo tempo: acima disso responde 429 Too Many Requests, e cada requisição a mais em andamento deixa as outras mais lentas. Compare Promise.all sem limite com um pool de concorrência.

–pico de simultâneas
–com sucesso
–respostas 429

Uma linha por requisição, da esquerda (início) para a direita (fim). Verde-azulado: sucesso. Vermelho: 429.

Ver o código

Sem limite: tudo de uma vez

await Promise.all(contratos.map((c) => api.cotacao(c.id)))
// 40 requisições no mesmo instante

Pool: no máximo N ao mesmo tempo

async function comLimite(tarefas, limite) {
  const resultados = []
  let proxima = 0
  async function trabalhador() {
    while (proxima < tarefas.length) {
      const i = proxima++
      resultados[i] = await tarefas[i]()
    }
  }
  await Promise.all(Array.from({ length: limite }, trabalhador))
  return resultados
}

// Na prática: p-limit
const limite = pLimit(5)
await Promise.all(contratos.map((c) => limite(() => api.cotacao(c.id))))

Controlar a carga: no cliente, no servidor ou na API?

O limite no cliente protege o servidor de um navegador. O servidor precisa se proteger de todos os navegadores juntos. As duas coisas são necessárias, e a melhor solução muitas vezes é não fazer quarenta chamadas.

No cliente

Pool e backoff

  • Limite de 4 a 6 simultâneas por tarefa em lote (uploads, sincronização).
  • No 429 ou 503: respeite o Retry-After e use backoff exponencial com jitter, para que todos não tentem de novo no mesmo instante.
  • Cancele com AbortController o que a pessoa não precisa mais.
No servidor

Limites e filas

  • Rate limiting por usuário ou IP, devolvendo 429 com Retry-After.
  • Pool de conexões do banco: o número de queries simultâneas é limitado, o resto espera.
  • Fila (SQS, BullMQ) para trabalho pesado: responde 202 na hora e processa no ritmo que o sistema aguenta.
  • Backpressure: recusar cedo é melhor que aceitar tudo e cair.
Na API externa

Cota de terceiros

  • APIs pagas limitam requisições por minuto: o limite precisa ser global, no servidor, não por aba.
  • Cacheie respostas que não mudam (cotação de 5 minutos atrás serve para a maioria das telas).
  • Agrupe chamadas iguais em andamento (deduplicação).
O melhor caso

Endpoint em lote

Uma requisição com 40 ids troca 40 idas e voltas por uma. Se o backend é do seu time, peça: POST /cotacoes { ids: [...] }.

Dividir em lotes fixos de 6 (esperar o lote inteiro antes do próximo) é pior que o pool: o lote anda no ritmo da requisição mais lenta.

Leitura de sênior. Promise.all em uma lista que vem de dados não tem limite: hoje são 10 itens, amanhã são 500, e o seu próprio app derruba a API ou gasta a cota do mês. Limite a concorrência, trate o 429 com backoff e, antes de tudo isso, pergunte se dá para pedir tudo numa requisição só.
