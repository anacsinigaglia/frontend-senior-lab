Experimento · Core Web Vitals

As três notas que o Google dá para a sua página

Core Web Vitals são três métricas de experiência real: quanto o conteúdo principal demora a aparecer, quanto a tela demora a responder e quanto o layout pula. Os números abaixo são medidos ao vivo nesta página, com a mesma API que a biblioteca web-vitals usa. Provoque uma interação lenta e um layout que pula, e veja a nota mudar.

INP ruim: trabalha antes de pintar

botao.onclick = () => {
  recalcularCarteira()               // 300 ms travando a thread
  status.textContent = 'Salvo'       // só pinta depois
}

INP bom: responde, cede a thread, trabalha

botao.onclick = async () => {
  status.textContent = 'Salvando…'   // resposta visível já
  await depoisDaPintura()            // rAF + setTimeout
  recalcularCarteira()
  status.textContent = 'Salvo'
}

Leitura de sênior. A nota que conta é a de campo: o Google usa o percentil 75 das visitas reais do Chrome (CrUX), não o seu notebook. O Lighthouse mede LCP e CLS em laboratório, mas não mede INP, porque não clica em nada: no lugar ele mostra o TBT, que só aproxima. Para INP, use a aba Performance do DevTools (que mostra as três métricas ao vivo enquanto você usa a página) e a web-vitals em produção. O React Profiler não mede nenhuma das três: ele entra depois, quando a aba Performance mostrou que o tempo está no React.

Experimento · Debounce

Quantas buscas cada tecla dispara?

Um campo de busca que chama a API a cada tecla sobrecarrega o servidor e mostra resultados piscando. Digite com e sem debounce e compare o número de requisições.

Digite a mesma frase com 0 ms e depois com 300 ms.

0teclas
0requisições
0%evitadas
    Ver o código 
    // Espera a pessoa parar de digitar por `ms` antes de chamar fn
function debounce(fn, ms) {
  let timer
  return (...args) => {
    clearTimeout(timer)                       // cada tecla cancela a anterior
    timer = setTimeout(() => fn(...args), ms)
  }
}

// Em React, o equivalente é debounçar o valor:
const [busca, setBusca] = useState('')
const buscaAtrasada = useDebouncedValue(busca, 300)
const { data } = useQuery({
  queryKey: ['clientes', buscaAtrasada],
  queryFn: () => api.clientes(buscaAtrasada),
})

    Leitura de sênior. Debounce resolve chamadas caras disparadas por eventos frequentes (busca, resize, autosave). Se o custo é renderizar e não chamar a rede, prefira useDeferredValue, que mantém o campo responsivo sem atrasar o que a pessoa digita.

    Experimento · Virtualização

    Uma tabela com 50 mil linhas

    O navegador precisa criar, estilizar e posicionar cada elemento do DOM. Virtualizar significa desenhar só as linhas visíveis. Aumente o número de linhas e compare o tempo e a quantidade de elementos.

    Estratégia

    Role a lista nos dois modos. No modo virtual, o número de elementos continua pequeno.

    –tempo de render + layout
    –elementos no DOM
    Ver o código 
    // Virtualização na mão: só desenha o que cabe na janela
const ALTURA = 32
const inicio = Math.floor(caixa.scrollTop / ALTURA)
const fim = inicio + Math.ceil(caixa.clientHeight / ALTURA)
espacador.style.height = total * ALTURA + 'px'   // mantém a barra de rolagem real
for (let i = inicio; i < fim; i++) desenhaLinha(i, i * ALTURA)

// Na prática: @tanstack/react-virtual
const v = useVirtualizer({ count: linhas.length, getScrollElement: () => ref.current, estimateSize: () => 32 })
v.getVirtualItems().map(item => <Linha key={item.key} style={{ transform: `translateY(${item.start}px)` }} />)

    Virtualizar, paginar ou filtrar no servidor?

    As três não competem: resolvem gargalos diferentes. Virtualizar reduz o custo de desenhar (os dados já estão no navegador, o DOM é que pesa). Paginar ou filtrar no servidor reduz o custo de buscar e trafegar. Pergunte: está lento porque o navegador desenha demais, ou porque chega dado demais?

    Virtualizar

    Quando é melhor

    • O volume é limitado e cabe no cliente: milhares a dezenas de milhares de linhas leves, poucos MB. Ex.: os clientes de um assessor, um extrato do ano.
    • A pessoa percorre a lista em vez de procurar um item: rola, compara linhas vizinhas, navega pelo teclado.
    • Ordenar e filtrar precisam ser instantâneos: com tudo em memória, nenhum clique vira requisição.
    • Os dados chegam em fluxo: logs, feed, cotações, chat.
    • Precisa funcionar offline ou com rede ruim depois de carregado.
    • As linhas têm altura previsível.
    Paginar / filtrar no servidor

    Quando é melhor

    • O volume é grande ou não tem limite: virtualizar não salva um JSON de 50 MB.
    • A pessoa procura um item específico: busca e filtro levam direto a ele.
    • Permissão e segurança: o que ela não pode ver nem deve chegar ao navegador.
    • Totais e agregações precisam bater com o banco, mesmo com dados mudando.
    • URL compartilhável ou SEO: ?page=3&status=ativo.
    Custos da virtualização

    O que você paga

    • O Ctrl+F do navegador não acha linhas fora da tela.
    • Leitor de tela não sabe o tamanho da lista sem aria-rowcount e aria-rowindex.
    • Altura variável exige medir cada linha e pode causar “pulos” no scroll.
    • Impressão, restaurar a posição do scroll e cabeçalho fixo com largura de coluna dão trabalho extra.
    • Abaixo de algumas centenas de linhas simples, não precisa de nenhuma das técnicas.
    O caso comum

    Combinar as duas

    Lista grande que a pessoa rola: scroll infinito com paginação por cursor no servidor e virtualização no cliente. O servidor entrega em blocos, o cliente desenha só o visível, e o filtro fica no servidor para não buscar o que vai ser descartado.

    Em React: useInfiniteQuery (TanStack Query) + useVirtualizer (TanStack Virtual).

    Leitura de sênior. Antes de virtualizar, pergunte se alguém precisa ver 50 mil linhas. Virtualize quando o problema é o DOM e os dados cabem no cliente. Pagine ou filtre no servidor quando o problema é o volume ou a busca. Quando são os dois, use os dois.

    Experimento · Layout thrashing

    Ler e escrever no DOM, intercalado ou em lote

    Ler uma medida como offsetWidth logo depois de mudar um estilo obriga o navegador a recalcular o layout na hora. Num loop, isso vira centenas de recálculos. Rode os dois modos e compare.

    –intercalado
    –em lote
    –diferença

    Intercalado: força layout a cada volta

    for (const el of caixas) {
  const w = el.offsetWidth          // lê (força layout)
  el.style.width = w + 10 + 'px'    // escreve (invalida)
}

    Em lote: um layout só

    const larguras = caixas.map(el => el.offsetWidth)  // lê tudo
caixas.forEach((el, i) => {
  el.style.width = larguras[i] + 10 + 'px'          // escreve tudo
})

    Leitura de sênior. Em React você raramente escreve esse loop, mas ele aparece em animações feitas à mão, em useLayoutEffect e em bibliotecas de terceiros. No painel Performance do DevTools, ele aparece como blocos roxos de "Layout" com o aviso Forced reflow.
