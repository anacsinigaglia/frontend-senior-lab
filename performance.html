Meça antes de otimizar

Otimizar sem medir só deixa o código mais complexo. Aqui você provoca três problemas clássicos, vê o número mudar e entende qual ferramenta resolve cada um.

  • Começa pelo sintomaPergunta o que está lento e para quem antes de escrever um useMemo.
  • Sabe onde o tempo vaiDistingue rede, JavaScript, layout e pintura no painel Performance.
  • Escolhe a ferramenta mais barataDebounce e paginação resolvem mais casos do que bibliotecas novas.

Experimento · Debounce

Quantas buscas cada tecla dispara?

Um campo de busca que chama a API a cada tecla sobrecarrega o servidor e mostra resultados piscando. Digite com e sem debounce e compare o número de requisições.

Digite a mesma frase com 0 ms e depois com 300 ms.

0teclas
0requisições
0%evitadas
    Ver o código 
    // Espera a pessoa parar de digitar por `ms` antes de chamar fn
function debounce(fn, ms) {
  let timer
  return (...args) => {
    clearTimeout(timer)                       // cada tecla cancela a anterior
    timer = setTimeout(() => fn(...args), ms)
  }
}

// Em React, o equivalente é debounçar o valor:
const [busca, setBusca] = useState('')
const buscaAtrasada = useDebouncedValue(busca, 300)
const { data } = useQuery({
  queryKey: ['clientes', buscaAtrasada],
  queryFn: () => api.clientes(buscaAtrasada),
})

    Leitura de sênior. Debounce resolve chamadas caras disparadas por eventos frequentes (busca, resize, autosave). Se o custo é renderizar e não chamar a rede, prefira useDeferredValue, que mantém o campo responsivo sem atrasar o que a pessoa digita.

    Experimento · Virtualização

    Uma tabela com 50 mil linhas

    O navegador precisa criar, estilizar e posicionar cada elemento do DOM. Virtualizar significa desenhar só as linhas visíveis. Aumente o número de linhas e compare o tempo e a quantidade de elementos.

    Estratégia

    Role a lista nos dois modos. No modo virtual, o número de elementos continua pequeno.

    –tempo de render + layout
    –elementos no DOM
    Ver o código 
    // Virtualização na mão: só desenha o que cabe na janela
const ALTURA = 32
const inicio = Math.floor(caixa.scrollTop / ALTURA)
const fim = inicio + Math.ceil(caixa.clientHeight / ALTURA)
espacador.style.height = total * ALTURA + 'px'   // mantém a barra de rolagem real
for (let i = inicio; i < fim; i++) desenhaLinha(i, i * ALTURA)

// Na prática: @tanstack/react-virtual
const v = useVirtualizer({ count: linhas.length, getScrollElement: () => ref.current, estimateSize: () => 32 })
v.getVirtualItems().map(item => <Linha key={item.key} style={{ transform: `translateY(${item.start}px)` }} />)

    Leitura de sênior. Antes de virtualizar, pergunte se alguém precisa ver 50 mil linhas. Paginação ou filtro no servidor costumam ser a resposta melhor. Virtualização tem custos: o Ctrl+F do navegador não encontra o que está fora da tela e alturas variáveis complicam o cálculo.

    Experimento · Layout thrashing

    Ler e escrever no DOM, intercalado ou em lote

    Ler uma medida como offsetWidth logo depois de mudar um estilo obriga o navegador a recalcular o layout na hora. Num loop, isso vira centenas de recálculos. Rode os dois modos e compare.

    –intercalado
    –em lote
    –diferença

    Intercalado: força layout a cada volta

    for (const el of caixas) {
  const w = el.offsetWidth          // lê (força layout)
  el.style.width = w + 10 + 'px'    // escreve (invalida)
}

    Em lote: um layout só

    const larguras = caixas.map(el => el.offsetWidth)  // lê tudo
caixas.forEach((el, i) => {
  el.style.width = larguras[i] + 10 + 'px'          // escreve tudo
})

    Leitura de sênior. Em React você raramente escreve esse loop, mas ele aparece em animações feitas à mão, em useLayoutEffect e em bibliotecas de terceiros. No painel Performance do DevTools, ele aparece como blocos roxos de "Layout" com o aviso Forced reflow.
