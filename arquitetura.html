Módulo · Arquitetura e estado

Cada estado tem um lugar certo

A maioria dos problemas de arquitetura no front vem de estado no lugar errado: dado do servidor copiado para um store global, prop passando por cinco componentes que não a usam, filtro que some quando a página recarrega. Aqui você vê o custo de cada escolha.

  • Separa servidor de clienteDado da API é cache e pertence ao React Query. useState fica com o que é da interface.
  • Mantém o estado perto de quem usaSobe o estado só quando precisa, e só até o pai comum mais próximo.
  • Pensa no link compartilhadoFiltro, aba e página moram na URL.

Experimento · Quem renderiza de novo

Prop drilling, Context ou store

O App guarda o tema e o usuário logado. Três componentes no fundo da árvore usam esses dados. Troque o tema ou o usuário e veja quais componentes renderizam de novo em cada abordagem.

Abordagem

    Ver o código das três abordagens 
    // Props: cada camada recebe e repassa, mesmo sem usar
<Layout tema={tema} usuario={usuario}> → <Sidebar tema={tema}> → <Menu tema={tema}> → <ThemeToggle tema={tema} />

// Context: some o repasse, mas todo consumidor renderiza quando QUALQUER campo muda
const AppCtx = createContext()
<AppCtx.Provider value={{ tema, usuario }}>...
const { usuario } = useContext(AppCtx)   // UserBadge renderiza ao trocar o tema

// Store com seletor (Zustand): cada componente assina só o que lê
const useApp = create(set => ({ tema: 'claro', usuario: 'Ana', trocarTema: () => set(...) }))
const usuario = useApp(s => s.usuario)   // ignora mudanças de tema

    O que é um store com seletor

    Um store é um objeto de estado que vive fora da árvore do React, com as funções que o alteram. Qualquer componente lê dele sem Provider e sem repasse de props. O seletor é a função que cada componente passa para dizer qual pedaço quer: (s) => s.usuario. Quando o store muda, a biblioteca roda o seletor de cada componente e compara o resultado com o anterior (Object.is). Só renderiza quem viu o próprio pedaço mudar. No modo "Store com seletor" acima, trocar o tema não acorda o UserBadge.

    Criar o store (Zustand v5)

    import { create } from 'zustand'

const useApp = create((set) => ({
  tema: 'claro',
  usuario: 'Ana',
  trocarTema: () => set((s) => ({
    tema: s.tema === 'claro' ? 'escuro' : 'claro',
  })),
}))

    Ler com seletor

    // só renderiza quando usuario muda
const usuario = useApp((s) => s.usuario)
const trocarTema = useApp((s) => s.trocarTema)

// sem seletor: renderiza a cada mudança do store
const tudo = useApp()

// vários campos de uma vez: useShallow
import { useShallow } from 'zustand/react/shallow'
const { tema, usuario } = useApp(
  useShallow((s) => ({ tema: s.tema, usuario: s.usuario })),
)

    Context × store

    Context avisa todos os consumidores quando o value muda, mesmo quem só lê um campo que não mudou. O store com seletor avisa só quem lê o campo que mudou.

    Pegadinha: seletor que cria objeto

    useApp((s) => ({ a: s.a, b: s.b })) devolve um objeto novo a cada vez. Para a comparação, ele "sempre mudou": renderiza à toa e, no Zustand v5, pode entrar em loop infinito. Use useShallow ou um seletor por campo.

    Seletor também deriva

    useApp((s) => s.contratos.length) só renderiza quando a contagem muda, não a cada edição de contrato. É o estado derivado do experimento abaixo, calculado na leitura.

    Quando vale

    Estado de cliente lido em muitos lugares distantes e que muda com frequência: carrinho, cotações ao vivo, editor. Dado da API vai para o React Query, não para o store. Tema e usuário logado cabem em Context.

    Leitura de sênior. Repassar prop por duas ou três camadas é normal e fácil de rastrear. Context funciona bem para valores que mudam pouco (tema, usuário, idioma). Store com seletor compensa quando muitos componentes leem partes diferentes de um estado que muda com frequência.

      Leitura de sênior. Dado do servidor não é estado da aplicação, é uma cópia que pode estar velha. Uma biblioteca de cache resolve deduplicação, revalidação, cancelamento e retry. Copiar a resposta para Redux ou Context é recriar essa biblioteca com bugs.

      Experimento · Estado derivado

      O total que fica velho

      Se um valor pode ser calculado a partir de outro estado ou de uma prop, ele não é estado: é derivado. Guardar os dois em useState cria duas fontes da verdade, e cada mudança precisa lembrar de atualizar as duas. Os botões abaixo mexem nos dois painéis ao mesmo tempo: à esquerda, três estados mantidos à mão; à direita, um estado e o resto calculado no render.

      Filtro de grão

      Estado duplicado: contratos + filtrados + total

      Derivado: contratos + filtro, o resto calculado

      Sempre em sincronia: é calculado a cada render

      Teste: clique em "+100 sc no primeiro" e veja o total da esquerda não mudar. Depois troque o filtro: ele "conserta" tudo, porque o handler do filtro recalcula. O bug só aparece quando alguém esquece um set, e é por isso que passa no teste rápido.

      Três estados para manter em sincronia

      const [contratos, setContratos] = useState(inicial)
const [filtrados, setFiltrados] = useState(inicial)
const [total, setTotal] = useState(somar(inicial))

function adicionar(c) {
  setContratos([...contratos, c])
  setTotal(total + c.sacas)   // ignora o filtro
}                             // esqueceu setFiltrados
function editar(id, sacas) {
  setContratos(contratos.map(...))  // esqueceu setTotal
}

      Quantos renders cada jeito custa

      Além de ficar velho, o estado duplicado costuma custar render extra. Clique para adicionar um contrato e veja a linha do tempo de cada componente. O mais comum, sincronizar com useEffect, renderiza duas vezes, e a primeira mostra o total velho.

      Calculado no render

      const total = somar(contratos)

        0 renders

        useState + set no mesmo handler

        setContratos(novos)
setTotal(total + c.sacas)

          0 renders

          useState + useEffect para sincronizar

          useEffect(() => {
  setTotal(somar(contratos))
}, [contratos])

            0 renders

            Desde o React 18, vários set no mesmo evento viram um render (batching): o problema do meio é ficar fora de sincronia, não render a mais. Já o useEffect só roda depois que a tela foi pintada, então o segundo set sempre gera outro render, e cada filho renderiza de novo junto. Calcular no render nunca acrescenta render. Se a conta for cara, useMemo evita refazer a conta, não o render.

            A mesma armadilha com props: copiar a prop para o estado

            useState(cliente.obs) só lê a prop na primeira renderização. Quando o pai troca de cliente, o título acompanha (vem da prop), mas o campo continua com o texto antigo. Escolha outro cliente e compare.

            Dá para calcular? Não é estado

            Antes de criar um useState, pergunte se o valor sai de outro estado, de uma prop ou da URL. Totais, listas filtradas, contagens, "tem erro?", "está tudo marcado?", nome completo: tudo isso é uma conta no render.

            useEffect para sincronizar é o mesmo bug, mais lento

            useEffect(() => setTotal(somar(contratos)), [contratos]) renderiza duas vezes: a primeira com o total velho na tela, a segunda corrigida. Veja o contador de renders acima. Além de mais lento, espalha a lógica. Calcule direto.

            Guarde o id, não a cópia do objeto

            const [selecionado, setSelecionado] = useState(contrato) guarda uma cópia que não vê as edições. Guarde selecionadoId e derive: contratos.find((c) => c.id === selecionadoId).

            Booleanos que se contradizem

            isLoading, isError e data separados podem chegar a combinações impossíveis. É o mesmo problema: um status só, e o resto derivado dele. Veja o experimento em Qualidade e testes.

            Leitura de sênior. Estado é o mínimo que não dá para calcular. Cada useState a mais é uma fonte da verdade que alguém precisa lembrar de atualizar. Quando dois estados precisam mudar juntos, normalmente um deles é derivado do outro, e o bug aparece no dia em que alguém esquece um set.
