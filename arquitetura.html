Módulo · Arquitetura e estado

Cada estado tem um lugar certo

A maioria dos problemas de arquitetura no front vem de estado no lugar errado: dado do servidor copiado para um store global, prop passando por cinco componentes que não a usam, filtro que some quando a página recarrega. Aqui você vê o custo de cada escolha.

  • Separa servidor de clienteDado da API é cache e pertence ao React Query. useState fica com o que é da interface.
  • Mantém o estado perto de quem usaSobe o estado só quando precisa, e só até o pai comum mais próximo.
  • Pensa no link compartilhadoFiltro, aba e página moram na URL.

Experimento · Quem renderiza de novo

Prop drilling, Context ou store

O App guarda o tema e o usuário logado. Três componentes no fundo da árvore usam esses dados. Troque o tema ou o usuário e veja quais componentes renderizam de novo em cada abordagem.

Abordagem
–renderizaram agora
–sem necessidade

    Ver o código das três abordagens 
    // Props: cada camada recebe e repassa, mesmo sem usar
<Layout tema={tema} usuario={usuario}> → <Sidebar tema={tema}> → <Menu tema={tema}> → <ThemeToggle tema={tema} />

// Context: some o repasse, mas todo consumidor renderiza quando QUALQUER campo muda
const AppCtx = createContext()
<AppCtx.Provider value={{ tema, usuario }}>...
const { usuario } = useContext(AppCtx)   // UserBadge renderiza ao trocar o tema

// Store com seletor (Zustand): cada componente assina só o que lê
const useApp = create(set => ({ tema: 'claro', usuario: 'Ana', trocarTema: () => set(...) }))
const usuario = useApp(s => s.usuario)   // ignora mudanças de tema

    Leitura de sênior. Repassar prop por duas ou três camadas é normal e fácil de rastrear. Context funciona bem para valores que mudam pouco (tema, usuário, idioma). Store com seletor compensa quando muitos componentes leem partes diferentes de um estado que muda com frequência.
