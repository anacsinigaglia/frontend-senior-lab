Module · Architecture and state

Every piece of state has a right place

Most frontend architecture problems come from state in the wrong place: server data copied into a global store, a prop passed through five components that don't use it, a filter that disappears on reload. Here you see the cost of each choice.

  • Separates server from clientAPI data is a cache and belongs to React Query. useState keeps what belongs to the UI.
  • Keeps state close to where it's usedLifts state only when needed, and only up to the nearest common parent.
  • Thinks about the shared linkFilter, tab and page live in the URL.

Prop drilling, Context or store

App holds the theme and the logged-in user. Three components deep in the tree use that data. Change the theme or the user and see which components re-render with each approach.

    See the code for the three approaches 
    // Props: every layer receives and passes along, even without using it
<Layout theme={theme} user={user}> → <Sidebar theme={theme}> → <Menu theme={theme}> → <ThemeToggle theme={theme} />

// Context: no more passing, but every consumer renders when ANY field changes
const AppCtx = createContext()
<AppCtx.Provider value={{ theme, user }}>...
const { user } = useContext(AppCtx)   // UserBadge renders when the theme changes

// Store with selector (Zustand): each component subscribes only to what it reads
const useApp = create(set => ({ theme: 'light', user: 'Ana', toggleTheme: () => set(...) }))
const user = useApp(s => s.user)   // ignores theme changes

    What a store with selectors is

    A store is a state object that lives outside the React tree, along with the functions that change it. Any component reads from it with no Provider and no prop passing. The selector is the function each component passes to say which piece it wants: (s) => s.user. When the store changes, the library runs each component's selector and compares the result with the previous one (Object.is). Only components whose piece changed re-render. In the "Store with selector" mode above, changing the theme doesn't wake up UserBadge.

    Create the store (Zustand v5)

    import { create } from 'zustand'

const useApp = create((set) => ({
  theme: 'light',
  user: 'Ana',
  toggleTheme: () => set((s) => ({
    theme: s.theme === 'light' ? 'dark' : 'light',
  })),
}))

    Read with a selector

    // only re-renders when user changes
const user = useApp((s) => s.user)
const toggleTheme = useApp((s) => s.toggleTheme)

// no selector: re-renders on every store change
const everything = useApp()

// several fields at once: useShallow
import { useShallow } from 'zustand/react/shallow'
const { theme, user } = useApp(
  useShallow((s) => ({ theme: s.theme, user: s.user })),
)

    Context vs. store

    Context notifies every consumer when its value changes, even those reading a field that didn't change. A store with selectors only notifies whoever reads the field that changed.

    Gotcha: a selector that builds an object

    useApp((s) => ({ a: s.a, b: s.b })) returns a new object every time. To the comparison it "always changed": it re-renders for nothing and, in Zustand v5, can loop forever. Use useShallow or one selector per field.

    Selectors derive too

    useApp((s) => s.contracts.length) only re-renders when the count changes, not on every contract edit. It's the derived state from the experiment below, computed at read time.

    When it pays off

    Client state read in many distant places that changes often: a cart, live quotes, an editor. API data belongs in React Query, not in the store. Theme and the logged-in user fit in Context.

    Senior take. Passing a prop through two or three layers is normal and easy to trace. Context works well for values that rarely change (theme, user, language). A store with selectors pays off when many components read different parts of state that changes often.

    Two screens request the same clients

      Senior take. Server data isn't application state. It's a copy that may be stale. A caching library handles deduplication, revalidation, cancellation and retry. Copying the response into Redux or Context is rebuilding that library, with bugs.

      Experiment · Derived state

      The total that goes stale

      If a value can be computed from other state or from a prop, it isn't state: it's derived. Keeping both in useState creates two sources of truth, and every change has to remember to update both. The buttons below change both panels at once: on the left, three pieces of state kept in sync by hand; on the right, one piece of state and the rest computed during render.

      Grain filter

      Duplicated state: contracts + filtered + total

      Derived: contracts + filter, the rest computed

      Always in sync: computed on every render

      Try it: click "+100 bags on the first one" and watch the total on the left stay the same. Then change the filter: it "fixes" everything, because the filter handler recalculates. The bug only shows up when someone forgets a set, which is why it passes a quick test.

      Three pieces of state to keep in sync

      const [contracts, setContracts] = useState(initial)
const [filtered, setFiltered] = useState(initial)
const [total, setTotal] = useState(sum(initial))

function add(c) {
  setContracts([...contracts, c])
  setTotal(total + c.bags)    // ignores the filter
}                             // forgot setFiltered
function edit(id, bags) {
  setContracts(contracts.map(...))  // forgot setTotal
}

      One piece of state; the rest is math

      const [contracts, setContracts] = useState(initial)
const [grain, setGrain] = useState('all')

// recomputed on every render: it can't go stale
const filtered = grain === 'all'
  ? contracts
  : contracts.filter((c) => c.grain === grain)
const total = filtered.reduce((s, c) => s + c.bags, 0)

      Can you compute it? It isn't state

      Before adding a useState, ask whether the value comes from other state, a prop or the URL. Totals, filtered lists, counts, "is there an error?", "is everything checked?", a full name: all of these are math during render.

      Syncing with useEffect is the same bug, slower

      useEffect(() => setTotal(sum(contracts)), [contracts]) renders twice: first with the stale total on screen, then corrected. Besides being slower, it scatters the logic. Compute it directly.

      Store the id, not a copy of the object

      const [selected, setSelected] = useState(contract) keeps a copy that never sees edits. Store selectedId and derive: contracts.find((c) => c.id === selectedId).

      Booleans that contradict each other

      Separate isLoading, isError and data can reach impossible combinations. Same problem: one status, with the rest derived from it. See the experiment in Quality & testing.

      Senior take. State is the minimum you can't compute. Every extra useState is a source of truth someone has to remember to update. When two pieces of state must change together, one of them is usually derived from the other, and the bug shows up the day someone forgets a set.
