The right tag does half the work

A <button> comes with focus, keyboard support and a screen reader announcement. A <div> comes with none of that. In the experiments below, you test with the keyboard, hear what a screen reader would announce, and measure contrast.

  • Picks the tag by behaviorA link navigates, a button performs an action. Looks are CSS's job.

What type="submit", "button" or no type changes

<button> is the element: something clickable that performs an action. type says what it does inside a form, just like <input type="text"> and <input type="checkbox"> are the same element with different behavior. The confusing part: without a type, a button is submit. That's why type="button" exists: it means "a plain button that doesn't submit".

Try it: click each button, press Enter in the field, and try saving with the field empty or with an invalid email.

    Inside a <form>A click…Use it for
    type="submit" (the default)validates the fields and fires the form's submit. Enter in a text field does the same.the button that saves or sends
    type="button"does nothing on its own: it only runs your onClickeverything else: Cancel, Show password, + Add, open a menu
    type="reset"restores the fields to their initial valuesalmost never: wiping what the user typed is usually an accident

    Classic bug: the button without a type submits

    <form onSubmit={save}>
  <input type="password" />
  <button onClick={togglePassword}>👁</button>  // submits the form!
  <button onClick={save}>Save</button>          // Enter skips this
</form>

    Right: one submit path, handled on the form

    <form onSubmit={(e) => { e.preventDefault(); save(new FormData(e.currentTarget)) }}>
  <input type="password" name="password" required />
  <button type="button" onClick={togglePassword}>👁</button>  // doesn't submit
  <button type="submit">Save</button>  // click and Enter
</form>

    Outside a <form>, type changes nothing. With two submit buttons, e.nativeEvent.submitter (in React) or e.submitter tells you which one was clicked, and its name/value goes along with the data. When the submit button is disabled, Enter stops submitting too.

    Senior take. If you are writing role="button" and tabIndex, stop and switch to <button>. The same goes for links: if the action changes the URL, use <a href>. That way people can open it in a new tab and the back button works.

        What navigation shortcuts are

        Sighted users glance at the page and go straight to what matters. Screen reader users can't, and listening to everything in order would take minutes. So the screen reader builds lists of the page's elements and offers keys to jump between them. Those lists only include real elements: the <div class="ttl"> in the card on the left doesn't make it into the headings list.

        Key (NVDA and JAWS)Jumps to the next…Comes from
        H or 1–6heading (or heading of that level)<h1>–<h6>
        D (NVDA) / R (JAWS)region (landmark)<header>, <nav>, <main>, <aside>, <footer>
        Klink<a href>
        Bbutton<button>
        Fform field<input>, <select>, <textarea>
        Ttable<table>
        Llist<ul>, <ol>

        In VoiceOver: the rotor

        In NVDA and JAWS, Shift plus the key goes back to the previous one. On the Mac and iPhone, the equivalent is the rotor: VO+U on the Mac, or a two-finger twist on the iPhone screen. It opens the lists of headings, links, regions and fields.

        In WebAIM's survey of screen reader users, navigating by headings is the most common way to look for information on a page.

        A shortcut you build: the skip link

        It is hidden and shows up on the first Tab. It moves focus straight to the content, so keyboard users don't tab through the whole menu on every page.

        <a class="skip" href="#content">Skip to content</a>
…
<main id="content">…</main>

        How to test it

        Turn on VoiceOver (⌘+F5) on one of your pages, open the rotor (VO+U) and read only the headings list. If it reads like the page's table of contents, the structure is good. If it is empty or full of "Click here", it isn't yet.

        Senior take. Screen reader users often jump from heading to heading (the H key) or from region to region. Without <h3> and <nav>, they have to listen to the whole page line by line. Also note "Cancel order #1042": in a list, ten buttons named just "Cancel" do not say which order each one cancels.

        Experiment · Contrast

        Can you read this text in sunlight?

        WCAG requires a minimum contrast of 4.5:1 for normal text and 3:1 for large text. Test your design system's colors or the examples.

        Examples
        142.5 bags sold Average price of R$ 128.40 per bag last week.
        –contrast
        See the calculation 
        // Relative luminance (WCAG 2.x)
const channel = v => (v /= 255) <= 0.03928 ? v / 12.92 : ((v + 0.055) / 1.055) ** 2.4
const lum = ([r, g, b]) => 0.2126 * channel(r) + 0.7152 * channel(g) + 0.0722 * channel(b)

const contrast = (a, b) => {
  const [light, dark] = [lum(a), lum(b)].sort((x, y) => y - x)
  return (light + 0.05) / (dark + 0.05)       // from 1:1 to 21:1
}

        Senior take. Color should never be the only signal. An "overdue" status in red also needs text or an icon, because about 8% of men have some form of color blindness.

        Experiment · Beyond accessibility

        What the right element gives you for free

        Semantic HTML is not only for screen readers. The browser, search engines, phones and testing tools depend on it too. Start with the two "links" below: they look the same and go to the same place.

        <div onClick>

        Go to the contrast experiment

        <a href>

        Go to the contrast experiment

        Try both:

        • ⌘/Ctrl + click, or middle click: does it open a new tab?
        • Right click: is there a "Copy link address" option?
        • Hover: does the URL show up in the corner of the window?
        • Tab: does focus reach it?

        Only the <a href> does all of this without a single line of JavaScript. And search engines only follow real links.

        1. Built-in behavior

        • <a href>: new tab, copy link, history and prefetch.
        • <button> in a <form>: submits on Enter, respects disabled and joins native validation (required, type="email").
        • <details>, <dialog> and popover: open, close, Esc and focus, with no library.

        2. Phones and autofill

        type="email", "tel" and "number" open the right keyboard on phones. autocomplete="email", "one-time-code" and "current-password" let the browser and the password manager fill fields in for you.

        3. Less JavaScript, more robustness

        Native elements are implemented by the browser itself: less code in the bundle and fewer handlers. The page works before the JS loads and when it fails: a link is still a link and a form still submits.

        4. SEO

        Google discovers pages by following <a href>: navigation built with onClick isn't crawled. Headings, <main>, <article> and <nav> tell it what is main content and what is menu or footer.

        5. Other tools read the structure

        Safari and Firefox reader mode, the browser's translator, printing, extensions and AI agents browsing for you all use <main>, <article>, headings and <table> with <th> to know what matters.

        6. Tests that don't break for no reason

        Testing Library and Playwright query elements by role. With semantic HTML this just works, and the test survives class and layout changes. With <div> you are left with data-testid, which tests the implementation instead of what the user sees.

        screen.getByRole('button', { name: 'Save' })

        7. Code that explains itself

        <nav><ul><li><a> says what it is. <div class="nav-wrapper"> makes you open the CSS and the JS. In code review, it also exposes intent bugs: a "button" that navigates should be a link.

        8. New features land on native elements

        <dialog>, popover, customizable <select> and <search>: the browser keeps evolving on top of the standard elements, and whoever already uses them gets the new features for free.

        Senior take. Before putting an onClick on a <div>, ask whether an element already does that. It almost always does, and it brings keyboard support, accessibility, SEO and better tests along with it.
