Module · Rendering & caching

Where and when the page is built

SSG, ISR, SSR and CSR are not project styles. They are answers to three questions about the data. Is it the same for everyone? How often does it change? Can it arrive a few seconds old? Here you see what each answer costs in load time, API calls and SEO.

  • Decides by the data, not by fashionAsks who sees the content and how often it changes before picking a strategy.
  • Thinks in cache, not in modesIn the App Router, rendering follows from what can be cached and for how long.
  • Mixes them on the same pageStatic shell, cached block and per-user part streamed in.

Experiment · The four strategies

And SEO in each one?

        
For SEO, two things matter: what is in the HTML the crawler receives and how fast the page loads, because Core Web Vitals count toward ranking.

        

          

            SSG and ISR
            
The best case

            
    
              
  • Full HTML, served by the CDN: low TTFB and LCP.
    • 
              
  • With ISR, the crawler sometimes sees a version a few minutes old, which almost never matters.
    • 
            

          

          

            SSR
            
Good, if the API is fast

            
    
              
  • The content is in the HTML.
    • 
              
  • A slow API becomes a high TTFB, which hurts LCP and the score.
    • 
            

          

          

            CSR
            
The worst case

            
    
              
  • The HTML arrives with an empty <div id="root">.
    • 
              
  • Google runs JS, but in a second queue, later and with no guarantee.
    • 
              
  • Link previews (WhatsApp, LinkedIn, Slack), other search engines and AI crawlers often do not run JS.
    • 
            

          

          

            Watch the label
            
Client Component is not CSR

            
In Next, a component with 'use client' is also rendered on the server on the first load and then hydrated. SEO only suffers when the data is fetched in the browser.

            
Title, description and Open Graph come from metadata or generateMetadata, always on the server. A logged-in area is not indexed: SEO does not apply there.

          

        

      

      
Senior take. SSG and ISR win at almost everything, but they only work for content that is the same for everyone. The deciding question is not "which one is faster" but "can this HTML be the same for every person?". If it can, cache it. If it cannot, use SSR with streaming. Leave CSR for what comes after the interaction.

    


    

      

        
Experiment · Revalidation

        
The price changed. Who still sees the old one?

        
ISR uses stale-while-revalidate: when the cache expires, the next visit gets the old version right away and triggers regeneration in the background. Whoever arrives after that gets the new one. Change the price in the database, make visits and see who saw the old price in each revalidation mode. Here the time limit is 10 s, and regenerating takes 1.5 s.

    On demand: signal when it changes
    

    // CMS webhook or Route Handler called by the backend
revalidateTag('prices', 'max')    // next visits: old, then new

// Server Action of whoever just edited
'use server'
await pricesApi.update(id, value)
updateTag('prices')               // whoever saved already sees the new one
    
        
    
      
    
      
    Senior take. A fixed time limit is simple, but it fails in both directions: it regenerates for nothing when nothing changed, and it keeps the old price until the limit expires. When the backend knows when the data changes, revalidate on demand with revalidateTag and use a long time limit only as a safety net. For whoever just saved, use updateTag: nobody accepts editing a price and seeing the old one on the next screen.

    // next.config.ts
const nextConfig = { cacheComponents: true }

// app/catalog/page.tsx
export default function CatalogPage() {
  return (
    <>
      <Header />                                      // static: goes in the shell
      <Products />                                    // 'use cache': goes in the shell
      <Suspense fallback={<GreetingSkeleton />}>
        <Greeting />                                  // reads cookies(): streamed in
      </Suspense>
    </>
  )
}

async function Products() {
  'use cache'
  cacheLife('hours')
  cacheTag('products')
  return <List items={await productsApi.list()} />
}
    
      
    
      
    Senior take. In the previous model, a single cookie read makes the whole route dynamic, and caching becomes all or nothing. With Cache Components (Partial Prerendering), what is static or cached goes in the shell served right away, and only the part that depends on the request is streamed inside the <Suspense>. React's cache(), which many people confuse with ISR, only avoids calling the same function twice in the same request.
