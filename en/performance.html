Experiment · Core Web Vitals

The three scores Google gives your page

Core Web Vitals are three real-experience metrics: how long the main content takes to appear, how long the screen takes to respond, and how much the layout jumps. The numbers below are measured live on this page, with the same API the web-vitals library uses. Trigger a slow interaction and a jumping layout, and watch the score change.

Why CLS has no unit

LCP is measured in seconds and INP in milliseconds. CLS is a score: every time something visible moves without the user asking for it, the browser computes

shift = impact fraction × distance fraction
  • Impact fraction: how much of the viewport the moved elements cover, counting both their old and new positions.
  • Distance fraction: how far they moved, divided by the viewport's largest dimension (usually the height).
  • Why "cumulative": shifts are added up in windows, less than 1 s apart and at most 5 s long. The page's CLS is the window with the largest sum, not the sum of the whole visit. That is why clicking the banner below several times doesn't make the number grow forever.

Example from this experiment, in a 900 px tall viewport: the 180 px banner pushes about 60% of the screen. 0.6 × (180 ÷ 900) ≈ 0.12, close to what the panel measures.

Lighthouse, the Performance panel or the React Profiler?

None of them is better: each one answers a different question. And DevTools is not an extension, it ships with Chrome (F12). The extension you install is React DevTools, and the React Profiler lives inside it.

DevTools Lighthouse panel

Does the page load well?

  • A 0–100 score with LCP, CLS and TBT, plus hints such as heavy images and unused JS.
  • It is a lab measurement: run it in an incognito tab with mobile throttling and compare before and after.
  • It doesn't measure INP, because it doesn't click anything.
DevTools Performance panel

Where did the time go?

  • A timeline of JS, style recalculation, layout and paint. Long tasks (over 50 ms) are flagged in red.
  • Shows LCP, INP and CLS live while you use the page.
  • The layout thrashing and 50,000-row experiments in this module show up here.
React DevTools extension

Which component rendered, and why?

  • Only sees React: how many times each component rendered and what it cost.
  • Turn on "Highlight updates" and "Record why each component rendered".
  • Doesn't measure any Core Web Vital.
The order

Assess, locate, pinpoint

Lighthouse gives the overall loading diagnosis. The Performance panel shows whether the bottleneck is JS, layout or paint. The React Profiler comes in when the Performance panel shows the time is spent in React.

In an app behind a login, the problem is usually interaction, not loading: you will use the last two the most.

Senior take. The score that counts is the field score: Google uses the 75th percentile of real Chrome visits (CrUX), not your laptop. Lighthouse measures LCP and CLS in the lab, but not INP, because it doesn't click anything: instead it shows TBT, which is only an approximation. For INP, use the DevTools Performance tab (which shows all three metrics live while you use the page) and web-vitals in production. The React Profiler measures none of the three: it comes in later, once the Performance tab has shown the time is spent in React.

Experiment · Debounce

How many searches does each key press fire?

A search field that calls the API on every key press overloads the server and makes results flicker. Type with and without debounce and compare the number of requests.

Type the same phrase at 0 ms and then at 300 ms.

0key presses
0requests
0%avoided
    See the code 
    // Wait until the user stops typing for `ms` before calling fn
function debounce(fn, ms) {
  let timer
  return (...args) => {
    clearTimeout(timer)                       // each key press cancels the previous one
    timer = setTimeout(() => fn(...args), ms)
  }
}

// In React, the equivalent is debouncing the value:
const [search, setSearch] = useState('')
const debouncedSearch = useDebouncedValue(search, 300)
const { data } = useQuery({
  queryKey: ['clients', debouncedSearch],
  queryFn: () => api.clients(debouncedSearch),
})

    Senior take. Debounce solves expensive calls fired by frequent events (search, resize, autosave). If the cost is rendering rather than hitting the network, prefer useDeferredValue, which keeps the field responsive without delaying what the user types.

    Experiment · Virtualization

    A table with 50 thousand rows

    The browser has to create, style and position every DOM element. Virtualizing means drawing only the visible rows. Increase the number of rows and compare the time and the element count.

    Strategy

    Scroll the list in both modes. In virtual mode, the element count stays small.

    –render + layout time
    –DOM elements
    See the code 
    // Hand-rolled virtualization: only draw what fits in the window
const HEIGHT = 32
const start = Math.floor(box.scrollTop / HEIGHT)
const end = start + Math.ceil(box.clientHeight / HEIGHT)
spacer.style.height = total * HEIGHT + 'px'      // keeps the real scrollbar
for (let i = start; i < end; i++) drawRow(i, i * HEIGHT)

// In practice: @tanstack/react-virtual
const v = useVirtualizer({ count: rows.length, getScrollElement: () => ref.current, estimateSize: () => 32 })
v.getVirtualItems().map(item => <Row key={item.key} style={{ transform: `translateY(${item.start}px)` }} />)

    Virtualize, paginate or filter on the server?

    The three don't compete: they solve different bottlenecks. Virtualizing cuts the cost of drawing (the data is already in the browser, the DOM is what weighs). Paginating or filtering on the server cuts the cost of fetching and transferring. Ask: is it slow because the browser draws too much, or because too much data arrives?

    Virtualize

    When it wins

    • The volume is bounded and fits on the client: thousands to tens of thousands of light rows, a few MB. E.g. an advisor's clients, a year's statement.
    • The user scans the list rather than looking for one item: scrolls, compares neighboring rows, navigates by keyboard.
    • Sorting and filtering must be instant: with everything in memory, no click becomes a request.
    • Data arrives as a stream: logs, feeds, quotes, chat.
    • It must work offline or on a bad network once loaded.
    • Rows have a predictable height.
    Paginate / filter on the server

    When it wins

    • The volume is large or unbounded: virtualizing won't save a 50 MB JSON.
    • The user looks for a specific item: search and filters take them straight to it.
    • Permissions and security: what they can't see shouldn't even reach the browser.
    • Totals and aggregates must match the database, even while data changes.
    • Shareable URL or SEO: ?page=3&status=active.
    Costs of virtualization

    What you pay

    • The browser's Ctrl+F can't find off-screen rows.
    • Screen readers don't know the list size without aria-rowcount and aria-rowindex.
    • Variable height means measuring each row and can cause scroll “jumps”.
    • Printing, restoring scroll position and a sticky header with column widths take extra work.
    • Below a few hundred simple rows, you need none of these techniques.
    The common case

    Combine both

    A large list the user scrolls: infinite scroll with cursor pagination on the server and virtualization on the client. The server delivers in chunks, the client draws only what's visible, and filtering stays on the server so you don't fetch what will be discarded.

    In React: useInfiniteQuery (TanStack Query) + useVirtualizer (TanStack Virtual).

    Senior take. Before virtualizing, ask whether anyone needs to see 50 thousand rows. Virtualize when the problem is the DOM and the data fits on the client. Paginate or filter on the server when the problem is volume or search. When it's both, use both.

    Experiment · Layout thrashing

    Reading and writing the DOM, interleaved or batched

    Reading a measurement like offsetWidth right after changing a style forces the browser to recalculate layout on the spot. In a loop, that becomes hundreds of recalculations. Run both modes and compare.

    –interleaved
    –batched
    –difference

    Interleaved: forces layout on every iteration

    for (const el of boxes) {
  const w = el.offsetWidth          // read (forces layout)
  el.style.width = w + 10 + 'px'    // write (invalidates)
}

    Batched: a single layout

    const widths = boxes.map(el => el.offsetWidth)      // read everything
boxes.forEach((el, i) => {
  el.style.width = widths[i] + 10 + 'px'            // write everything
})

    Senior take. In React you rarely write this loop, but it shows up in hand-made animations, in useLayoutEffect and in third-party libraries. In the DevTools Performance panel, it appears as purple "Layout" blocks with the Forced reflow warning.
