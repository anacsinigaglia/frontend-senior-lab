Module · Loading & network

Send less, later and in the right order

The screen is ready sooner when the browser downloads only what it needs now, finds critical files early and puts off the rest. The server also copes better when the client does not fire a hundred requests at once. Here you split a bundle, defer images, reorder the download waterfall, prefetch the next screen and limit concurrency.

  • Knows what goes in the first downloadOpens the bundle analyzer before arguing about frameworks.
  • Defers what is not visibleScreens, libraries and off-screen images load when they are used.
  • Protects the serverLimits concurrent requests and asks for a batch endpoint instead of a hundred calls.

How to find what is heavy

Optimizing a bundle without looking at it is guessing. The tools below show each dependency as a rectangle the size of the space it takes.

Analyze

Bundle analyzer

  • Vite: rollup-plugin-visualizer.
  • Next: next experimental-analyze (Turbopack) or @next/bundle-analyzer.
  • Before you install a package: bundlephobia.com shows its size and whether it supports tree shaking.
Usual suspects

What is often heavy

  • Date libraries with every locale, charts, editors, maps, PDF.
  • Duplicate packages in different versions.
  • Barrel files (an index.ts that re-exports everything) with side effects.
  • Polyfills for browsers you do not support.
The cost of splitting

Too many chunks also hurt

  • Each import() is a network round trip at the moment of use: the user sees a loading state that did not exist before.
  • Splitting off something of 3 KB is not worth it.
  • Preload the chunk when use is likely (on hover, at idle time).
What matters

Performance budget

Set a cap for the initial JS (for example, 170 compressed KB for mobile) and make CI fail when it goes over, with size-limit or the bundler's report. Without this, the bundle only grows.

Senior take. JavaScript costs twice: to download and, above all, for the phone to parse and run, while the main thread is busy (which makes INP worse). An image of the same size is much cheaper. Split by route (the framework usually does this), defer what only appears after a click, and measure before and after with the analyzer.

Senior take. Lazy loading is for what is off screen. Experiment · Preload, preconnect and fetchpriority

What does the browser find late?

The browser only downloads what it has already found. The font only shows up after the CSS is read; the app data, after the JavaScript runs. Each late discovery becomes a step in the waterfall. Turn on the resource hints and watch the steps disappear.

Connecting to a new domain (DNS, TCP and TLS) costs 250 ms in this model. Without high priority, the main image shares bandwidth with the JavaScript.

Senior take. Resource hints do not make anything lighter: they only start things earlier. That is why they work for what is critical and found late, and get in the way when used on everything. Open the Network tab, sort by the Waterfall column and look for the step: an important resource that only starts after another one finishes.

Experiment · Prefetching

Start fetching before the click

Each screen takes 700 ms to arrive from the server. Without prefetch, the user waits all of that after clicking. With prefetch, the fetch starts earlier: when the mouse hovers over the link or when the link appears on screen. Try each mode and compare the wait after the click with what was fetched for nothing.

Senior take. Prefetch trades data and server load for perceived speed. "On hover" is almost always right and wastes little: people take 100 to 300 ms between hovering and clicking. "When it appears" is the fastest and the most wasteful. Turn prefetch off on links to heavy, rarely used screens, and respect navigator.connection.saveData.

Experiment · Limited concurrency

A hundred requests at once. Who goes down?

Refreshing the quote for 40 contracts by calling the API once for each. The simulated API handles 6 requests at the same time: above that it returns 429 Too Many Requests, and each extra request in flight makes the others slower. Compare Promise.all with no limit against a concurrency pool.

No limit: everything at once

await Promise.all(contracts.map((c) => api.quote(c.id)))
// 40 requests at the same instant

Pool: at most N at the same time

async function withLimit(tasks, limit) {
  const results = []
  let next = 0
  async function worker() {
    while (next < tasks.length) {
      const i = next++
      results[i] = await tasks[i]()
    }
  }
  await Promise.all(Array.from({ length: limit }, worker))
  return results
}

// In practice: p-limit
const limit = pLimit(5)
await Promise.all(contracts.map((c) => limit(() => api.quote(c.id))))

Controlling load: in the client, the server or the API?

A limit in the client protects the server from one browser. The server has to protect itself from all browsers together. You need both, and the best solution is often to not make forty calls.

In the client

Pool and backoff

  • A limit of 4 to 6 concurrent requests per batch task (uploads, sync).
  • On a 429 or 503: respect Retry-After and use exponential backoff with jitter, so clients do not all retry at the same instant.
  • Cancel what the user no longer needs with AbortController.
In the server

Limits and queues

  • Rate limiting per user or IP, returning 429 with Retry-After.
  • Database connection pool: the number of concurrent queries is limited, and the rest wait.
  • Queue (SQS, BullMQ) for heavy work: reply 202 right away and process at the pace the system can handle.
  • Backpressure: refusing early is better than accepting everything and going down.
In the external API

Third-party quota

  • Paid APIs limit requests per minute: the limit must be global, in the server, not per tab.
  • Cache responses that do not change (a quote from 5 minutes ago is fine for most screens).
  • Merge identical calls that are already in flight (deduplication).
The best case

Batch endpoint

One request with 40 ids replaces 40 round trips with one. If your team owns the backend, ask for it: POST /quotes { ids: [...] }.

Splitting into fixed batches of 6 (waiting for the whole batch before the next) is worse than the pool: each batch moves at the pace of its slowest request.

Senior take. Promise.all over a list that comes from data has no limit: today it is 10 items, tomorrow it is 500, and your own app takes down the API or burns the monthly quota. Limit concurrency, handle 429 with backoff and, before all of that, ask whether you can get everything in a single request.
