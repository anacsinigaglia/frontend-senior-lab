Módulo · Renderização e cache

Onde e quando a página é montada

SSG, ISR, SSR e CSR não são estilos de projeto: são respostas a três perguntas sobre o dado. Ele é igual para todo mundo? Com que frequência muda? Pode chegar alguns segundos velho? Aqui você vê o custo de cada resposta em tempo de carregamento, chamadas à API e SEO.

  • Decide pelo dado, não pela modaPergunta quem vê o conteúdo e com que frequência ele muda antes de escolher a estratégia.
  • Pensa em cache, não em modoNo App Router, a renderização é consequência do que pode ficar em cache e por quanto tempo.
  • Mistura na mesma páginaCasca estática, bloco em cache e trecho por usuário em streaming.

Experimento · As quatro estratégias

A mesma página de produto, montada de quatro jeitos

Mude a latência da API e o tráfego e veja o que acontece com o tempo até o conteúdo aparecer, com a carga no servidor e com o que o robô do Google recebe. Os números vêm de um modelo simples, explicado abaixo dos controles: o que importa é a proporção entre as estratégias, não o milissegundo.

E o SEO em cada uma?

        
Para SEO, importam duas coisas: o que está no HTML que o robô recebe e quão rápido a página carrega, porque as Core Web Vitals entram no ranking.

        

          

            SSG e ISR
            
O melhor caso

            
    
              
  • HTML completo, servido pela CDN: TTFB e LCP baixos.
    • 
              
  • No ISR, o robô às vezes vê uma versão alguns minutos velha, o que quase nunca importa.
    • 
            

          

          

            SSR
            
Bom, se a API for rápida

            
    
              
  • O conteúdo está no HTML.
    • 
              
  • API lenta vira TTFB alto, que pesa no LCP e na nota.
    • 
            

          

          

            CSR
            
O pior caso

            
    
              
  • O HTML chega com um <div id="root"> vazio.
    • 
              
  • O Google executa JS, mas numa segunda fila, mais tarde e sem garantia.
    • 
              
  • Prévias de link (WhatsApp, LinkedIn, Slack), outros buscadores e crawlers de IA muitas vezes não executam JS.
    • 
            

          

          

            Cuidado com o rótulo
            
Client Component não é CSR

            
No Next, um componente com 'use client' também é renderizado no servidor no primeiro carregamento e depois hidratado. O SEO só sofre quando o dado é buscado no navegador.

            
Título, descrição e Open Graph saem de metadata ou generateMetadata, sempre no servidor. Área logada não é indexada: ali o SEO não se aplica.

          

        

      

      
Leitura de sênior. SSG e ISR ganham em quase tudo, mas só servem para conteúdo igual para todo mundo. A pergunta que decide não é "qual é mais rápida", e sim "esse HTML pode ser o mesmo para todas as pessoas?". Se pode, cacheie. Se não pode, SSR com streaming. Deixe o CSR para o que vem depois da interação.

    


    

      

        
Experimento · Revalidação

        
O preço mudou. Quem ainda vê o velho?

        
ISR usa stale-while-revalidate: quando o cache vence, a visita seguinte recebe a versão velha na hora e dispara a regeneração em segundo plano. Quem chega depois recebe a nova. Mude o preço no banco, faça visitas e veja quem viu o preço velho em cada modo de revalidação. Aqui o prazo é de 10 s, e regenerar leva 1,5 s.

    Sob demanda: avisa quando mudar
    

    // Webhook do CMS ou Route Handler chamado pelo backend
revalidateTag('precos', 'max')    // próximas visitas: velho, depois novo

// Server Action de quem acabou de editar
'use server'
await precosApi.atualizar(id, valor)
updateTag('precos')               // quem salvou já vê o novo
    
        
    
      
    
      
    Leitura de sênior. Prazo fixo é simples, mas erra para os dois lados: regenera à toa quando nada mudou e deixa o preço velho até o prazo vencer. Quando o backend sabe a hora em que o dado muda, revalide sob demanda com revalidateTag e use um prazo longo só como rede de segurança. Para quem acabou de salvar, use updateTag: ninguém aceita editar um preço e ver o antigo na tela seguinte.
    
    
    

    
    
      
    
        
    Experimento · Cache no Next.js
    
        
    O que torna a rota dinâmica?
    
        
    No App Router você não escolhe "SSR" ou "SSG" num arquivo de configuração: o Next olha o que cada parte da página faz e decide. Marque o que a página faz e compare o resultado no modelo anterior (o padrão até hoje) e com cacheComponents: true (Next 16).
    
      
    
      
    
        
    
          
    CamadaOnde ficaO que guardaQuanto tempo

        Ver o código

    // next.config.ts
const nextConfig = { cacheComponents: true }

// app/catalogo/page.tsx
export default function CatalogoPage() {
  return (
    <>
      <Cabecalho />                                   // estático: entra na casca
      <Produtos />                                    // 'use cache': entra na casca
      <Suspense fallback={<SaudacaoSkeleton />}>
        <Saudacao />                                  // lê cookies(): chega em streaming
      </Suspense>
    </>
  )
}

async function Produtos() {
  'use cache'
  cacheLife('hours')
  cacheTag('produtos')
  return <Lista itens={await produtosApi.list()} />
}
    
      
    
      
    Leitura de sênior. No modelo anterior, uma única leitura de cookie torna a rota inteira dinâmica, e o cache vira tudo ou nada. Com Cache Components (Partial Prerendering), o que é estático ou está em cache vai na casca servida na hora, e só o trecho que depende da requisição chega em streaming dentro do <Suspense>. O cache() do React, que muita gente confunde com ISR, só evita chamar a mesma função duas vezes na mesma requisição.
