Módulo · Qualidade e testes

Código que impede o erro de acontecer

Qualidade não é ter 100% de cobertura. É escrever tipos que não deixam montar um estado inválido e testes que quebram quando o comportamento quebra, e só nessa hora.

  • Modela estados com tiposUsa uma união de status em vez de três booleanos que podem se contradizer.
  • Testa o que a pessoa vêBusca por texto e papel, não por classe CSS ou variável interna.
  • Lembra dos estados esquecidosCarregando, erro e vazio são telas, não detalhes.

Experimento · Estados impossíveis

Três booleanos ou um status?

À esquerda, a tela é controlada por isLoading, isError e data, que podem ser ligados em qualquer combinação. À direita, um único status só permite estados válidos. Ligue as flags e procure combinações que não fazem sentido.

Três booleanos: 2³ = 8 combinações

Um status: 4 estados, todos válidos

Impossível montar uma tela contraditória.E o TypeScript só deixa ler data dentro do caso success.

Permite estados impossíveis

type Estado = {
  isLoading: boolean
  isError: boolean
  data?: Contrato[]
}
// { isLoading: true, isError: true, data: [...] } compila

União discriminada

type Estado =
  | { status: 'loading' }
  | { status: 'error'; erro: string }
  | { status: 'empty' }
  | { status: 'success'; data: Contrato[] }

switch (estado.status) {
  case 'success': return <Lista itens={estado.data} />  // data só existe aqui
  ...
}

Leitura de sênior. O React Query já devolve status como união. O ponto aqui é levar a mesma ideia para os seus próprios tipos: etapa de um wizard, situação de um contrato, permissão de usuário. Se dois campos não podem ser verdadeiros ao mesmo tempo, o tipo deveria impedir isso.

Experimento · Testes

Qual teste quebra numa refatoração?

Um contador de sacas tem três versões: a original, uma refatoração que muda só o código interno e uma com um bug real (o número não atualiza na tela). Rode as duas suítes contra cada versão. Um bom teste falha no bug e passa na refatoração.

      Pelo que a pessoa vê (Testing Library)

      it('mostra 10 sacas ao registrar uma venda', async () => {
  render(<Contador />)
  await user.click(screen.getByRole('button', { name: /registrar venda/i }))
  expect(screen.getByText(/10 sacas/)).toBeInTheDocument()  // resultado visível
})

      Leitura de sênior. Teste que quebra em toda refatoração ensina o time a ignorar teste vermelho. E buscar por papel e nome acessível testa a acessibilidade de graça: se getByRole('button') não encontra o elemento, um leitor de tela também não encontra.
